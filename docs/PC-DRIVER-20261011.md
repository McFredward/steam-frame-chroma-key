# Windows Steam Link encoder and frame association

Investigation: 2026-10-11, supplied Windows `driver_vrlink.dll`. This is a
version-specific static result, not an installed capture adapter or a successful
passthrough test. The previous [PC source report](PC-MASK-SOURCE.md) predates
receipt of this driver. No driver was loaded, patched or activated, and no Frame
file or process was modified.

## Result

Three boundaries are now concrete:

1. The inspected HMD exposes DirectMode 009 and DisplayComponent 003. Its
   component dispatcher does not expose VirtualDisplay 002; that version string
   elsewhere in the DLL is insufficient evidence. Consequently the public
   `PresentInfo_t.nFrameId` is not this driver's demonstrated frame source.
2. The inspected D3D11 composition output is NV12 or P010. These video formats
   have luma and chroma planes, with no retained alpha plane. Reading alpha from
   that final encoder texture cannot recover scene coverage.
3. The FEC transmitter assigns its own 16-bit key **after** an encoded frame and
   its presentation metadata have been queued together. The key is not obtained
   by truncating the first 32-bit presentation field.

The useful integration therefore needs a real coverage pass before RGB-to-YUV
conversion, paired with that exact encoder input and subsequently with its actual
transmitter key. An application submit counter or public mirror poll cannot
replace this association.

The [Frame receiver analysis](FRAME-ASSOCIATION-DATAFLOW.md) separately traces
that received key through decoding and metadata selection. Together these
results identify a concrete correspondence to test; they do not yet establish
a source session, wrap generation, a public 64-bit frame identity or eye UVs.

The explicit producer-to-encoder branch above is conditional. Other private
control/metadata paths exist, including a diagnostic called `wgp id`; neither
its expanded meaning nor its equivalence to this presentation counter is
established. The active connection version and selected producer must be
recorded before relying on either path.

## Alpha and implementation consequence

The embedded composition code samples four-component textures, and blend state
setup exists. That does not prove that application alpha is useful coverage or
that it survives all layer operations. The concrete final texture is already
YUV. Microsoft documents the [NV12 and P010 plane formats](https://learn.microsoft.com/en-us/windows/win32/api/dxgiformat/ne-dxgiformat-dxgi_format);
neither provides an independent alpha plane. A generic NVENC alpha-capability
string in the DLL is not proof that alpha-layer encoding is enabled here.

The public [OpenVR driver header](https://github.com/ValveSoftware/openvr/blob/0924064316de3effbcd1acf1e309182a2deb1c05/headers/openvr_driver.h)
defines the DirectMode method order used for the vtable check. Its `Present`
arguments contain the synchronization texture, without VirtualDisplay's
`nFrameId`. A transparent observer cannot manufacture that missing ID.

The next bounded PC implementation should first observe the active DirectMode
composition and encoder-input association, without replacing rendering. For a
real-mask export, compose a separate R8 coverage target from genuine source
alpha using the same acquired layers, bounds, eye selection and transforms as
the color pass. Keep a paired record through encoder input/output and bind it to
the actual TX-key allocation. GPU copies and mask transport belong on bounded
workers; the compositor thread must never wait for readback or network I/O.

Before mask use, runtime evidence must establish all of the following:

- The actual component, active producer branch, encoder backend and connection
  version for this driver hash.
- Texture pointer/handle, description, device, array slice and **reuse
  generation**, plus acquisition, GPU-completion and release ordering. A pointer
  or encoder slot alone is not an identity.
- One exact relation from source composition to encoder input/output and TX
  key, including drops, repeated presentation, connection reset and 16-bit wrap.
  Preserve separate producer-counter and transmitter-key domains.
- Real source coverage from an original test scene, including opaque red,
  opaque green, transparent black and partial coverage. The current PC mod's
  opaque clear requires an explicit real-alpha mode; no RGB key is acceptable.
- Stereo packing, crop, reprojection, foveation and decoded-to-render UV mapping.
  A correctly paired mask with unverified coordinates still stays disabled.

Missing evidence retains opaque rendering. No installable Steam Link mask bridge
or successful headset result is claimed by this investigation.
